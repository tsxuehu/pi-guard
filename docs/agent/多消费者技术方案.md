# 多消费者技术方案

## 1. 概述

pi-guard 的音视频链路中，三个核心模块采用了**统一的多消费者设计模式**：

| 模块 | 生产者 | 消费者典型场景 |
|---|---|---|
| `capture_video`（视频采集） | V4L2 采集线程 | 移动侦测、编码器、预览 |
| `capture_audio`（音频采集） | ALSA 采集线程 | 编码器、音频录制 |
| `processing_encoder`（编码器） | 视频/音频编码线程 | MP4 录制、RTMP 推流 |

这三个模块共享同一套设计思想：**单生产者线程产出数据，多个消费者独立、按需、以各自速率拉取**。本文档讲解这套方案的通用设计、关键机制，以及三个模块的具体实现差异。

---

## 2. 设计目标

### 2.1 为什么需要多消费者

以视频采集为例，一帧摄像头数据需要同时服务多个下游：
- **移动侦测**：每帧都要分析，但计算量大、处理慢
- **编码器**：25fps 实时编码，可能丢帧保新
- **预览**：按需取帧，可能 5fps 就够了

如果采用"生产者直接推送到消费者"的模型， fastest consumer 会拖慢整体；如果采用广播，慢消费者会丢数据。多消费者队列让**每个消费者按自己的节奏独立消费**，互不干扰。

### 2.2 核心诉求

| 诉求 | 说明 |
|---|---|
| 独立消费进度 | 消费者 A 处理到第 100 帧，消费者 B 可以刚从第 50 帧开始 |
| 自动资源回收 | 数据在所有消费者取走后才释放，避免悬空引用 |
| 队列容量可控 | 防止慢消费者拖垮内存，超限时丢弃最老数据 |
| 消费者动态增减 | 运行时可以注册/注销消费者，不影响其他消费者 |

## 3. 核心架构

### 3.1 单生产者-多消费者模型

```mermaid

    PL -->|"入队 + notify_all()"| Q["分发队列<br/>QueuedItem[ pending_consumers ]"]

    Q -->|"wait(id, last_seq)"| C1["消费者 A"]
    Q -->|"wait(id, last_seq)"| C2["消费者 B"]

    C1 -->|"update last_seq"| C1
    C2 -->|"update last_seq"| C2
    C3 -->|"update last_seq"| C3
```

### 3.2 数据流动时序

```
T0（初始）: consumers = {A, B}

时刻 T1: 生产者产出 Frame#1，pending = {A, B}，入队，notify_all
         消费者 A wait 返回，取走 Frame#1
         Frame#1 pending = {B}

时刻 T2: 生产者产出 Frame#2，pending = {A, B}，入队，notify_all
         消费者 B wait 返回，取走 Frame#1~#2
         Frame#1 pending = {} → 从队列移除，资源释放
         Frame#2 pending = {A}

时刻 T3: 消费者 C 注册，consumers = {A, B, C}
         C 调用 wait，但 Frame#2 的 pending = {A}，不包含 C
         C 阻塞等待（已有队列节点不会追加新消费者）

时刻 T4: 生产者产出 Frame#3，pending = {A, B, C}，入队，notify_all
         唤醒 C，C 取走 Frame#3（新消费者从注册后的数据开始消费）
```

## 4. 核心数据结构

多消费者方案涉及两层结构：**帧/包本身**（携带 `seq`、时间戳、负载数据）和**队列节点**（包装帧/包，附加 `pending_consumers` 追踪信息）。

### 4.1 帧/包结构：seq 的定义位置

三个模块的帧/包结构各不相同，但都包含 `seq` 字段作为全局递增序列号：

**视频帧**（[`video_frame.hpp`](file:///home/tsxuehu/workspace-daoqi/pi-guard/project/agent/src/modules/capture/video/include/capture_video/video_frame.hpp)）
```cpp
struct VideoFrame {
    uint64_t seq;               // 全局序列号（由 VideoCaptureProvider 递增分配）
    uint64_t timestamp_ns{};    // 采集时刻（steady_clock epoch，纳秒），便于与音频共时间轴
    void* data;                 // V4L2 mmap 内存映射地址
    size_t length;              // 帧大小（字节）
    std::shared_ptr<void> v4l2_ref;  // 引用计数：所有持有者释放后自动执行 VIDIOC_QBUF
};
```

**音频帧**（[`audio_frame.hpp`](file:///home/tsxuehu/workspace-daoqi/pi-guard/project/agent/src/modules/capture/audio/include/capture_audio/audio_frame.hpp)）
```cpp
struct AudioFrame {
    uint64_t seq;                       // 全局序列号（由 AudioCaptureProvider 递增分配）
    std::vector<int16_t> pcm_data;      // PCM S16_LE 交织数据
    uint64_t timestamp_ns;              // 采集时刻（steady_clock epoch，纳秒）
};
```

**编码包**（[`encoder_types.hpp`](file:///home/tsxuehu/workspace-daoqi/pi-guard/project/agent/src/modules/processing/encoder/include/processing_encoder/encoder_types.hpp)）
```cpp
struct EncodedPacketBase {
    uint64_t seq{0};            // 全局序列号（由 Encoder 递增分配）
    std::vector<uint8_t> data;  // 编码后的码流数据
    int64_t pts{0};             // 显示时间戳
    int64_t dts{0};             // 解码时间戳
    virtual ~EncodedPacketBase() = default;
};

struct EncodedVideoPacket : public EncodedPacketBase {
    bool key_frame{false};      // 是否为关键帧
};

struct EncodedAudioPacket : public EncodedPacketBase {};
```

三者的 `seq` 字段含义一致，区别在于：

| 维度 | VideoFrame | AudioFrame | EncodedPacketBase |
|---|---|---|---|
| seq 生成者 | `VideoCaptureProvider` | `AudioCaptureProvider` | `Encoder` |
| seq 计数器 | `global_seq_` | `next_seq_` | `packet_seq_` |
| 赋值时机 | DQBUF 出队后、入队列前 | ALSA readi 后、入队列前 | 编码完成后、入 packet_queue 前 |
| 时间戳字段 | `timestamp_ns` | `timestamp_ns` | `pts` / `dts` |
| 特殊字段 | `v4l2_ref`（QBUF 回收） | `pcm_data`（PCM 样本） | `data`（编码码流）、`key_frame` |

### 4.3 序列号：seq 与 last_seq

每帧/每包携带一个 **`seq`（全局递增序列号）**，由生产者线程在入队时分配，是整个多消费者方案的**消费进度追踪基石**。

#### 生成方式

三个模块各自维护独立的递增计数器，在 `state_mtx_` 保护下递增赋值：

| 模块 | 计数器 | 赋值代码 |
|---|---|---|
| 视频采集 | `global_seq_` | `frame->seq = ++global_seq_` |
| 音频采集 | `next_seq_` | `af->seq = next_seq_++` |
| 编码器 | `packet_seq_` | `packet->seq = ++packet_seq_` |

#### seq vs timestamp_ns

帧/包同时携带 `seq` 和 `timestamp_ns`，二者职责不同：

| 维度 | `seq` | `timestamp_ns` |
|---|---|---|
| 语义 | 数据产出顺序的严格序号 | 采集时刻的物理时间 |
| 保证 | **严格递增**，无重复、无回退 | 单调不递减，但同一时刻可能有多帧 |
| 用途 | 消费进度追踪、增量拉取、资源回收判断 | 音画同步、PTS 计算、时间相关逻辑 |
| 精度 | 整数，无精度问题 | 纳秒级，受系统时钟精度影响 |

简单说：**`seq` 回答"这是第几个"，`timestamp_ns` 回答"什么时候产生的"**。`seq` 不适合用于时间计算，`timestamp_ns` 也不适合用于消费进度追踪（同时间戳的帧无法区分先后）。

#### last_seq：消费者的游标

每个消费者维护一个 **`last_seq`**，记录自己上次消费到的最大序列号。每次调用 `wait_*()` 时传入 `last_seq`，Provider 只返回 `seq > last_seq` 的数据，消费者处理完后将 `last_seq` 推进到最后一帧/包的 `seq`：

```cpp
// ConsumerBase / AudioConsumerBase 中的典型消费循环
while (running_) {
    auto frames = provider->wait_frame(consumer_id_, last_seq_);  // 只取新数据
    if (frames.empty()) break;
    process(frames);
    last_seq_ = frames.back()->seq;  // 游标推进
}
```

这保证了：
- **增量拉取**：消费者只获取自己尚未消费的数据，不会重复、不会遗漏
- **独立进度**：不同消费者的 `last_seq` 互不影响，可以按各自速率消费
- **资源回收判断**：当某帧/包的 `seq <=` 所有活跃消费者的 `last_seq`，说明无人再需要它，可以从队列中移除

### 4.4 设计要点

- **`pending_consumers`**：记录还有哪些消费者没取走这帧/包。为空时，该节点可从队列中移除。
- **`shared_ptr`**：实际数据通过 `shared_ptr` 持有，节点移除时引用计数减 1。当最后一个引用（队列 + 所有消费者）释放时，数据才真正销毁。
- **队列容器选择**：视频和编码器用 `deque`（频繁头部弹出）；音频用 `list`（迭代器稳定性更好，但实际差异不大）。

## 5. 消费者生命周期

### 5.1 注册：register_consumer()

```cpp
consumer_id_t register_consumer() {
    std::lock_guard lock(state_mtx_);
    const consumer_id_t id = next_consumer_id_++;
    active_consumers_.insert(id);          // 加入活跃消费者集合
    return id;
}
```

- 在 `state_mtx_` 保护下分配递增的唯一 ID
- 新消费者不会自动获得历史数据；它需要在下次 `wait_*()` 时从队列中筛选未消费的节点

### 5.2 拉取：wait_*(consumer_id, last_seq)

```cpp
std::vector<std::shared_ptr<Frame>> wait_frame(consumer_id_t id, uint64_t last_seq) {
    std::unique_lock lock(state_mtx_);

    // 阻塞等待：有新帧且该消费者未消费
    state_cv_.wait(lock, [this, id, last_seq] {
        if (!running_) return true;
        for (const auto& item : queue_) {
            if (item.frame->seq > last_seq && item.pending_consumers.count(id) > 0)
                return true;
        }
        return false;
    });

    // 收集所有该消费者未消费的帧
    std::vector<std::shared_ptr<Frame>> result;
    for (const auto& item : queue_) {
        if (item.frame->seq > last_seq && item.pending_consumers.count(id) > 0) {
            result.push_back(item.frame);
        }
    }

    // 标记为已消费
    cleanup_consumer_pending_locked(id, last_seq, false);
    return result;
}
```

**关键设计**：
- 使用**谓词等待**（predicate wait），避免虚假唤醒问题
- 返回的是**批量数据**（`vector`），不是单帧，减少锁竞争
- `last_seq` 由消费者自己维护，每次取到数据后更新为最后一帧的 `seq`

### 5.3 注销：unregister_consumer()

```cpp
void unregister_consumer(consumer_id_t id) {
    std::lock_guard lock(state_mtx_);
    active_consumers_.erase(id);
    cleanup_consumer_pending_locked(id, 0, true);  // clear_all = true
    state_cv_.notify_all();
}
```

- 从活跃消费者集合移除
- `clear_all = true`：将该消费者从所有历史节点的 `pending_consumers` 中移除
- 通知所有等待中的消费者（它们可能正在等这帧）

| 维度 | VideoCaptureProvider | AudioCaptureProvider | Encoder |
|---|---|---|---|

## 7. 关键机制详解

### 7.1 引用计数与资源回收（视频采集的特殊性）

视频采集模块面临一个独特问题：V4L2 的帧数据是 `mmap` 映射的内核缓冲区，**必须在使用完毕后通过 `VIDIOC_QBUF` 还回驱动**，否则驱动会很快耗尽缓冲区而停止采集。

解决方案：**`shared_ptr` 自定义删除器 + `pending_consumers` 双重引用计数**。

```cpp
// 1. 出队时创建帧，绑定 QBUF 删除器
frame->v4l2_ref = std::shared_ptr<void>(nullptr, [fd, idx](void*) {
    v4l2_buffer b{};
    b.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    b.memory = V4L2_MEMORY_MMAP;
    b.index = idx;
    ioctl(fd, VIDIOC_QBUF, &b);  // 还回驱动
});

// 2. 入队时，frame 被 shared_ptr 持有（引用计数 +1）
queue_.push_back({frame, active_consumers_});

// 3. 消费者 wait_frame 返回时，result 中又持有 shared_ptr（引用计数 +N）

// 4. 所有消费者取走后，队列节点被 erase，shared_ptr 销毁
//    当最后一个引用（队列 + 所有消费者）释放时，删除器执行 QBUF
```

```mermaid
sequenceDiagram
    participant DQBUF as V4L2 DQBUF
    participant Q as 分发队列
    participant A as 消费者 A
    participant B as 消费者 B

    DQBUF->>Q: 创建 frame(v4l2_ref) → 入队
    Note over Q: shared_ptr 引用计数 = 1（队列持有）
    Q->>A: wait_frame 返回 → A 持有 shared_ptr
    Q->>B: wait_frame 返回 → B 持有 shared_ptr
    Note over A,B: 引用计数 = 3（队列 + A + B）
    A->>A: 处理完释放 → 引用计数 -1
    B->>B: 处理完释放 → 引用计数 -1 → 变为 0
    Note over Q: 队列节点 erase + 消费者释放 → 删除器执行 QBUF
```

该设计的好处是**不需要知道消费者什么时候用完**，只要 `shared_ptr` 的引用计数归零，QBUF 自动发生。队列节点移除和消费者释放是两个独立事件，最终由引用计数保证正确性。

### 7.2 队列溢出处理

三个模块在队列满时的策略一致：**丢弃最老的数据**。

```cpp
while (queue_.size() > max_capacity) {
    queue_.pop_front();  // 最老帧被移除
}
```

这意味着**慢消费者会丢失数据**，这是预期行为：
- 视频：旧帧是"过去"的画面，丢弃不影响实时性
- 音频：虽然原则上不应丢采样，但 1 秒缓冲对大多数场景够用
- 编码包：消费者处理跟不上时（磁盘 IO 慢、网络卡），丢包保内存

如果业务不能容忍丢数据，应增大容量或优化消费者处理速度，而不是改变丢弃策略。

### 7.3 同步前置知识：mutex 与 condition_variable

本方案的线程同步基于 `std::mutex` 和 `std::condition_variable` 两个 C++ 原语。

**mutex（互斥锁）**保护共享数据，确保同一时刻只有一个线程访问：

```cpp
std::mutex mtx;
int shared_data = 0;

// 线程 A
{
    std::lock_guard<std::mutex> lock(mtx);  // 加锁，离开作用域自动解锁
    shared_data++;
}

// 线程 B
{
    std::lock_guard<std::mutex> lock(mtx);  // 如果 A 持有锁，此处阻塞直到 A 解锁
    shared_data--;
}
```

- `lock_guard`：RAII 包装，构造时加锁、析构时解锁，适合简单场景
- `unique_lock`：更灵活，支持手动加锁/解锁，配合条件变量使用

**condition_variable（条件变量）**实现线程间的等待-通知协作，避免轮询：

```cpp
std::mutex mtx;
std::condition_variable cv;
bool ready = false;

// 等待线程
std::unique_lock<std::mutex> lock(mtx);
cv.wait(lock, [&] { return ready; });  // ready 为 false 时阻塞，为 true 时返回
// wait 内部等价于：while (!predicate()) { lock.unlock(); 等待通知; lock.lock(); }

// 通知线程
{
    std::lock_guard<std::mutex> lock(mtx);
    ready = true;
}  // 解锁
cv.notify_all();  // 唤醒所有等待线程
```

关键要点：

| 概念 | 说明 |
|---|---|
| 谓词等待 | `cv.wait(lock, predicate)` 等价于 `while (!predicate()) { cv.wait(lock); }`，避免虚假唤醒 |
| wait 的锁行为 | `wait` 阻塞时**自动释放锁**，被唤醒时**重新获取锁**，通知线程可正常获取锁 |
| notify_one vs notify_all | 多消费者场景必须用 `notify_all`，一个通知可能满足多个消费者 |
| 虚假唤醒 | 即使没有 `notify`，`wait` 也可能偶尔返回，必须用谓词检查条件是否真正满足 |

本方案中，每个 Provider/Encoder 都有自己独立的 `state_mtx_` + `state_cv_`，生产者入队后 `notify_all()`，消费者 `wait()` 等待新数据，就是上述模式的具体实例。

### 7.4 锁的粒度

模块的共享状态分为两类，各自由独立的锁保护：

**数据通路状态**（`state_mtx_` 保护，所有模块共有）

生产者入队、消费者拉取、注册/注销消费者都操作这些数据，是模块运行时的核心共享状态：

| 受保护的数据 | 说明 |
|---|---|
| `running_` | 生产者线程运行标志 |
| `active_consumers_` | 活跃消费者集合 |
| `queue_` | 分发队列 |
| `next_consumer_id_` / `next_seq_` | ID 生成器 |

**启动握手状态**（`start_mtx_` 保护，仅视频/音频采集模块）

只在 `start()` 期间使用，硬件初始化完成后不再访问：

| 受保护的数据 | 说明 |
|---|---|
| `start_reported_` | 生产者线程是否已回传启动结果 |
| `start_ok_` | 启动是否成功 |

两类状态分属不同锁，纯粹为了**概念清晰**——启动握手和数据通路是两个独立的关注点，各自的锁保护各自的状态，互不干扰。技术上两个条件变量可以共用一把互斥锁，但混在一起会让代码的意图变得模糊，也增加误用的风险。编码器不操作硬件，无需启动握手，因此只有 `state_mtx_`。

为什么 `state_mtx_` 不拆细锁？因为生产者的入队操作（"读 active_consumers_ + 写 queue_"）和消费者的出队操作（"读 queue_ + 写 pending_consumers"）高度耦合，拆锁反而增加死锁风险。当前场景下，锁竞争不激烈（生产者批量入队、消费者批量取出），一把锁更简单可靠。

### 7.5 消费者启动时的同步

视频和音频采集模块在启动时有一个额外的同步机制：**启动握手**——主线程调用 `start()` 时，需要等待生产者线程完成硬件初始化并回报结果，而非立即返回。

**涉及的四个字段**：

| 字段 | 类型 | 保护锁 | 说明 |
|---|---|---|---|
| `start_mtx_` | `std::mutex` | — | 保护启动握手状态（详见 7.4 锁的粒度） |
| `start_cv_` | `std::condition_variable` | `start_mtx_` | 通知主线程启动结果已就绪 |
| `start_reported_` | `bool` | `start_mtx_` | 生产者线程是否已回传启动结果 |
| `start_ok_` | `bool` | `start_mtx_` | 启动是否成功（V4L2/ALSA 初始化结果） |

```mermaid
sequenceDiagram
    participant Main as 主线程
    participant SM as start_mtx_ / start_cv_
    participant Prod as 生产者线程

    Main->>Main: running_ = true
    Main->>Prod: 创建线程（produce_loop）
    Prod->>Prod: init_hardware()
    alt 硬件初始化成功
        Prod->>SM: report_start_result(true)
        SM-->>Main: start_cv_ 唤醒
        Main->>Main: start_ok_ = true，start() 正常返回
        Prod->>Prod: 进入采集主循环
    else 硬件初始化失败
        Prod->>SM: report_start_result(false)
        SM-->>Main: start_cv_ 唤醒
        Main->>Main: start_ok_ = false，start() 抛异常
        Prod->>Prod: 线程退出
    end
```

为什么需要启动握手？
- `start()` 需要知道硬件初始化是否成功（V4L2/ALSA 打开失败）
- 如果没有这个同步，`start()` 立即返回后，调用方以为已经启动，实际硬件初始化失败，后续 `wait_*()` 永远等不到数据

编码器模块没有启动握手：Encoder 不直接操作硬件，其 `start()` 只需启动编码线程即可，不存在硬件初始化失败的可能，因此不需要这套握手机制。

### 7.6 生产者与消费者之间的同步

生产者与消费者的协作是本方案最核心的同步场景，涵盖**数据分发**和**资源回收**两条线索。

**数据分发时序**：

```mermaid
sequenceDiagram
    participant Prod as 生产者线程
    participant Lock as state_mtx_
    participant CV as state_cv_
    participant Q as 分发队列
    participant Cons as 消费者线程

    Prod->>Prod: 产出数据帧
    Prod->>Lock: lock()
    Prod->>Q: push_back({frame, pending_consumers})
    Prod->>Lock: unlock()
    Prod->>CV: notify_all()

    Note over Cons: 此前在 wait(lock) 中阻塞
    CV-->>Cons: 唤醒（lock 已自动释放）
    Cons->>Lock: lock()（wait 返回时自动重新获取）
    Cons->>Q: 收集 seq > last_seq 且 pending 的帧
    Q-->>Cons: 返回帧列表（shared_ptr 引用计数增加）
    Cons->>Q: cleanup_consumer_pending(id, last_seq)
    Cons->>Lock: unlock()
    Cons->>Cons: process(frames)（无锁，锁外处理）
    Cons->>Cons: last_seq = frames.back()->seq
```

**关键设计**：
- 消费者**持有锁等待**（`wait` 会自动释放锁并阻塞），所以生产者入队时不会阻塞
- 消费者拿到数据后**立即解锁**，数据处理在锁外进行，避免长时间持有锁

**谓词等待**：消费者使用谓词等待避免虚假唤醒：

```cpp
state_cv_.wait(lock, [this, id, last_seq] {
    if (!running_) return true;  // 停止时立即返回
    for (const auto& item : queue_) {
        if (item.frame->seq > last_seq && item.pending_consumers.count(id) > 0)
            return true;  // 有新帧可取
    }
    return false;  // 继续等待
});
```

`wait(predicate)` 内部等价于 `while (!predicate()) { wait(lock); }`，即使因为虚假唤醒或其他消费者的 notify 导致线程醒来，只要条件不满足就会继续等待。

**批量消费**：消费者不是每帧唤醒一次，而是一次取走所有未消费数据：

```cpp
// 消费者线程
while (running_) {
    auto frames = provider->wait_frame(id, last_seq);  // 可能一次返回 10 帧
    process(frames);                                    // 批量处理，无锁
    last_seq = frames.back()->seq;
}
```

相比之下，每次只取一帧需要频繁加锁、wait、notify，批量设计让条件变量的唤醒次数和锁的获取次数都大幅降低。

**三模块同步代码对比**：

| 模块 | 入队代码 | 唤醒方式 | 消费者等待条件 |
|---|---|---|---|
| Video | `lock` → `push_back` → `unlock` → `notify_all()` | `state_cv_.notify_all()` | `seq > last_seq && pending.count(id)` |
| Audio | `lock` → `push_back` → `unlock` → `notify_all()` | `state_cv_.notify_all()` | `seq > last_seq && pending.count(id)` |
| Encoder | `lock` → `push_back` → `unlock` → `notify_all()` | `state_cv_.notify_all()` | `seq > last_seq && pending.count(id)` |

三个模块的同步逻辑**完全一致**，区别仅在于数据类型和队列容量。

### 7.7 消费者停止时的同步

停止流程需要确保生产者线程和所有消费者线程安全退出，不丢数据、不泄漏资源。

**停止时序**：

```mermaid
sequenceDiagram
    participant Main as 主线程
    participant SM as state_mtx_ / state_cv_
    participant Prod as 生产者线程
    participant Cons as 消费者线程

    Main->>SM: running_ = false + notify_all()
    Note over Cons: wait(lock, predicate) 中阻塞
    SM-->>Cons: 唤醒，predicate 检查 running_ 为 false → 返回空结果
    Cons->>Cons: wait_*() 返回空 vector → 退出循环

    Note over Prod: 采集循环中检查 running_ 为 false → 退出循环
    Prod->>Prod: 释放硬件资源（stream off / unmap / close）

    Main->>Main: cap_thread_.join()
    Main->>Main: 消费者线程 join()
```

**关键设计**：
- `running_` 是所有线程的退出信号，受 `state_mtx_` 保护
- 主线程设置 `running_ = false` 后调用 `state_cv_.notify_all()`，所有阻塞在 `wait_*()` 的消费者都会醒来
- 消费者的谓词等待中 `!running_` 返回 `true`，`wait_*()` 返回空结果，消费者循环检测到空结果后退出
- 生产者线程在循环中检查 `running_`，为 false 时退出循环并释放硬件资源
- 主线程通过 `join()` 等待所有线程结束后才返回

**幂等 stop**：`stop()` 重复调用时仅执行 `join()`，不会重复释放硬件资源。通过 `mark_stopped()` 原子地设置 `running_ = false` 并返回此前是否处于运行态，保证清理逻辑只执行一次。

## 9. 设计决策与权衡

### 9.1 为什么选择"拉取"而非"推送"

| 模式 | 优点 | 缺点 |
|---|---|---|
| **拉取**（当前设计） | 消费者自己控制节奏，不会忙等；批量取减少锁竞争 | 消费者需要维护 `last_seq` |
| 推送（回调） | 实时性更高，代码更直观 | 慢消费者会阻塞生产者；需要背压机制 |

实时音视频场景下，**消费者处理速度差异大**（编码 25fps vs 移动侦测可能 5fps），拉取模式更适合。

### 9.2 为什么 pending_consumers 用集合而非计数器

用整数计数器似乎更简单（"还有 N 个消费者没取"），但用集合有两个优势：
1. **消费者注销时精准清理**：可以只移除特定消费者，不需要知道总数
2. **调试友好**：可以遍历看具体哪些消费者 pending，便于排查"谁没消费"

### 9.3 为什么音频和视频分开两套而不是共用一套模板

虽然设计模式高度相似，但三个模块保持独立实现的原因是：
1. **资源回收机制不同**：视频需要 V4L2 QBUF，音频和编码包不需要
2. **生命周期耦合不同**：视频帧和 V4L2 fd 强绑定，音频和 ALSA handle 绑定
3. **避免过度抽象**：C++ 模板元编程会增加编译时间和理解成本，当前代码量不大，显式重复更可维护

## 10. 常见问题

**Q：新注册的消费者能拿到历史数据吗？**

能。`wait_*()` 返回的是队列中所有 `seq > last_seq` 且该消费者 pending 的节点。新消费者的 `last_seq = 0`，所以会拿到队列中所有当前数据。但如果队列已满、旧数据已被丢弃，那新消费者只能拿到剩余数据。

**Q：消费者处理太慢会怎样？**

队列满时最老数据被丢弃。该消费者会看到 seq 跳跃（比如上次拿到 100，下次直接跳到 150），这是预期行为。

**Q：消费者崩溃/没调用 unregister 会怎样？**

如果消费者线程崩溃但没有释放 `ConsumerBase` / `AudioConsumerBase` 对象，析构函数里的 `unregister_consumer` 不会执行。该消费者的 ID 会一直留在 `pending_consumers` 中，导致队列节点永远无法释放，最终内存泄漏。生产环境中应确保消费者对象的生命周期受 RAII 管理。

**Q：为什么 `wait_*()` 返回 vector 而不是单帧？**

减少锁竞争。生产者批量入队、消费者批量取出，条件变量的唤醒次数降到最低。
